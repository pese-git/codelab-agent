# ADR-004: Стратегия эскалации при зацикливании агента на повторяющихся неудачах

**Дата:** 21 июля 2026  
**Статус:** Предложено  
**Контекст:** Поведение агента при многократных неудачных попытках выполнить задачу  
**Авторы:** —  
**Связанные документы:**
- `src/codelab/server/agent/loop/` — `AgentLoop`, итерации LLM tool-calling
- `src/codelab/server/agent/strategies/` — `StrategyDispatcher`, `SingleStrategy`
- `src/codelab/server/protocol/handlers/pipeline/stages/agent_loop.py` — точка интеграции
- Детектор зацикливания: `src/codelab/server/agent/loop/loop_detector.py`

---

## Контекст

При наблюдении за реальными сессиями обнаружен паттерн: агент застревает в цикле повторяющихся
неудачных попыток, не имея стратегии эскалации.

### Наблюдаемый паттерн (пример из логов 2026-07-21)

```
1. Агент пишет код → запускает тесты → тесты падают
2. Агент исправляет код → запускает тесты → тесты падают (другая ошибка)
3. Агент снова исправляет → снова тесты → снова падение
4. Повторяется 5-10 раз без прогресса
5. Пользователь вынужден вмешиваться вручную
```

**Конкретный случай:**
- Задача: написать код для Flutter-приложения
- Агент: 5 раз писал код, запускал `flutter test`, получал failures
- Результат: застрял, не смог решить задачу, пользователь прервал сессию
- Время: ~15 минут потеряно

### Корневые причины

1. **Отсутствие ограничения попыток:** `AgentLoop` продолжает итерации, пока LLM генерирует
   tool_calls. Нет механизма "стоп" при повторяющихся неудачах.

2. **Нет детекции паттерна "fix-test-fail":** Детектор зацикливания (`loop_detector.py`)
   ловит повторные вызовы **одного и того же инструмента** (например, `terminal/create` 4 раза
   подряд), но не ловит **семантическое зацикливание** (разные инструменты, но та же стратегия
   без прогресса).

3. **Отсутствие стратегии эскалации:** Агент не знает, когда остановиться и спросить
   пользователя. Нет fallback-стратегий (упростить задачу, предложить альтернативу,
   задокументировать проблему).

4. **Нет обратной связи от тестов:** Результат тестов (failure message) добавляется в историю,
   но агент не анализирует, что предыдущие попытки не удались. LLM может повторять те же
   подходы, если prompt не содержит явного указания изменить стратегию.

## Рассмотренные варианты

### A. Hardcoded limit на количество попыток

Добавить константу `MAX_TOOL_ITERATIONS = 20` в `AgentLoop`. После N итераций без `end_turn`
— принудительная остановка с уведомлением пользователя.

- ➕ Простая реализация, предсказуемое поведение
- ➕ Легко тестировать
- ➖ Негибко: сложные задачи могут требовать больше итераций
- ➖ Не различает "прогресс есть, но медленно" и "застрял"

### B. Configurable limit с детекцией прогресса

Добавить в конфигурацию `[agents.loop]`:
```toml
max_iterations = 50
max_consecutive_failures = 5
require_progress_every_n_iterations = 10
```

Детектор прогресса анализирует:
- Изменился ли `session.history` (новые tool results)
- Уменьшилось ли количество ошибок в тестах
- Меняется ли подход (разные tool_calls, не только разные аргументы)

Если прогресса нет N итераций подряд — эскалация.

- ➕ Гибко, настраивается под задачи
- ➕ Различает "медленно, но верно" и "застрял"
- ➖ Сложнее реализовать (нужен анализ истории)
- ➖ Ложные срабатывания, если эвристики неточные

### C. LLM-based meta-reasoning

Периодически (каждые N итераций) вызывать LLM с промптом:
"Проанализируй историю. Ты застрял? Если да — предложи альтернативную стратегию или
попроси помощи у пользователя."

- ➕ Умное решение, использует саму LLM для диагностики
- ➕ Может предложить креативные выходы
- ➖ Дорого (дополнительные LLM-вызовы)
- ➖ Ненадёжно: LLM может не признать, что застряла
- ➖ Усложняет debug

### D. Комбинация B + D: Configurable limit + user escalation

1. **Configurable limit** (вариант B) как базовая защита
2. **Эскалация к пользователю** при достижении лимита:
   - Отправить notification с анализом ситуации
   - Предложить варианты: "Продолжить", "Упростить задачу", "Отменить"
   - Пауза до ответа пользователя
3. **Fallback-стратегии** (если пользователь не отвечает или выбирает "авто"):
   - Попытаться упростить задачу (разбить на подзадачи)
   - Предложить альтернативный подход
   - Задокументировать проблему и остановиться

- ➕ Баланс автоматизации и контроля
- ➕ Пользователь остаётся в цикле принятия решений
- ➕ Можно расширять fallback-стратегии постепенно
- ➖ Требует UX для эскалации (notification, UI для выбора)
- ➖ Не все пользователи хотят вмешиваться (нужен auto-mode)

## Решение

**Принять вариант D (комбинация configurable limit + user escalation) как целевой.**

### Фазы реализации

**Фаза 1: Configurable limit + notification (MVP)**
1. Добавить в `AppConfig` секцию `[agents.loop]`:
   ```toml
   [agents.loop]
   max_iterations = 50
   max_consecutive_failures = 10
   ```
2. В `AgentLoop.run()` — счётчик итераций и consecutive failures
3. При достижении лимита — отправка `notification` пользователю:
   - Тип: `agent_stuck_detected`
   - Содержание: количество итераций, последние ошибки, предложение вмешаться
4. Поведение после notification:
   - Если пользователь отвечает `session/resume` → продолжить (сбросить счётчик)
   - Если пользователь отвечает `session/cancel` → остановиться
   - Если timeout (5 минут) → остановиться автоматически

**Фаза 2: Детекция прогресса**
1. Добавить в `AgentLoop` анализ `session.history`:
   - Сравнение последних N tool results (изменились ли результаты?)
   - Подсчёт уникальных tool names (меняется ли подход?)
2. Если прогресса нет `require_progress_every_n_iterations` — эскалация (как в Фазе 1)

**Фаза 3: Fallback-стратегии (опционально)**
1. При эскалации предложить варианты:
   - "Разбить задачу на подзадачи" (создать child sessions)
   - "Упростить задачу" (попросить пользователя уточнить)
   - "Попробовать альтернативный подход" (сменить стратегию/модель)
2. Реализовать автоматические fallback (если пользователь не вмешивается):
   - Автоматическое разбиение на подзадачи
   - Логирование проблемы для последующего анализа

### Критерии успеха

- Агент не застревает в бесконечных циклах
- Пользователь получает notification при обнаружении проблемы
- Время до эскалации: < 5 минут (настраиваемо)
- Ложные срабатывания: < 10% (агент не останавливается на сложных, но решаемых задачах)

## Последствия

### Позитивные
- **Предотвращение потери времени:** Пользователь узнаёт о проблеме быстро
- **Улучшение UX:** Контроль над поведением агента
- **Основа для дальнейших улучшений:** Детектор прогресса и fallback-стратегии можно
  расширять постепенно

### Негативные
- **Дополнительная сложность:** Нужна конфигурация, логика детекции, UI для эскалации
- **Риск ложных срабатываний:** Агент может останавливаться на сложных задачах prematurely
- **UX overhead:** Пользователю нужно отвечать на notifications (можно минимизировать auto-mode)

### Риски и mitigation

1. **Риск:** Ложные срабатывания на сложных задачах  
   **Mitigation:** Настраиваемые лимиты, возможность "продолжить" через `session/resume`

2. **Риск:** Пользователи игнорируют notifications  
   **Mitigation:** Auto-mode с fallback-стратегиями (Фаза 3), timeout с автоматической остановкой

3. **Риск:** Усложнение кодовой базы  
   **Mitigation:** Модульная реализация (3 фазы), детектор прогресса — опциональный модуль

## Связь с другими ADR

- **ADR-001** (LLM Adapter): Эскалация может потребовать смены модели/стратегии
- **ADR-002** (Context Manager): При эскалации контекст может быть перезапущен
- **ADR-003** (SessionState migration): Не влияет напрямую, но clean architecture упростит
  добавление новых компонентов (детектор прогресса, fallback-стратегии)
