# ADR-007. Владение состоянием сессии: транзакция на границе запроса

**Статус:** принято (2026-07-30)
**Контекст:** ADR-006 (перенос состояния сессии в домен, фаза D в работе), P0-39, P2-42
**Связано:** roadmap `2.1-double-cache-session-state.md` (решение де-факто откачено, см. ниже)

---

## Контекст

Два дефекта, найденных разбором живых логов, оказались следствиями одной причины — у состояния
сессии не было явно выбранного владельца:

* **P0-39** — `session/cancel` не останавливал turn. Сигнал отмены писался в `SessionState`, но
  идущий turn держал **другую копию**: `JsonFileStorage` отдаёт новый объект на каждый
  `load_session`. Обошли процессным реестром отмены.
* **P2-42** — `session/load` загружал сессию дважды за запрос и не сохранял ничего. Обработчик
  принимал решения (отмена вызовов, ответы модели, `cwd`) в копии, которую никто не записывал.

Замеры, на которых строится решение (2026-07-30, сессия 751 КБ, 53 вызова):

| Наблюдение | Значение |
|---|---|
| `load_session` возвращает новый объект каждому запросу | подтверждено (`a is b → False`) |
| Через порт домен не разделяется даже при кеше wire-объектов | подтверждено (`wire a is b → True`, `домен → False`) |
| Блокировки на сессию | отсутствуют |
| Атомарность записи | отсутствует (`json_file.py:71` пишет в целевой файл напрямую) |
| Ревизия документа | отсутствует (`schema_version` — версия формата) |
| Стоимость ввода-вывода | загрузка 1.8 мс, запись 4.2 мс |
| Состав документа | `tool_calls` 40%, `history` 29%, `events_history` 29% |

Итог: взяты издержки копий (нет общего состояния) без их защиты (нет CAS, нет атомарной
записи, нет блокировок).

**Определяющее свойство предметной области:** turn **не является одной транзакцией**. Он разорван
круговыми обменами с клиентом — запрос разрешения, клиентские RPC. Пересекающиеся запросы по
одной сессии — норма, а не исключение.

## Решение

### 1. Инвариант владения: транзакция на границе запроса

Состояние сессии принадлежит **транзакции**, а не процессу и не объекту. Порт — единственная
дверь; область транзакции явная:

```
async with repository.transaction(session_id) as session:
    ...
```

* одна загрузка на область (identity map внутри области, не дольше);
* блокировка на сессию на время области — против потери обновлений между пересекающимися
  запросами;
* commit при успешном выходе, отсутствие записи при исключении.

Это делает конструктивно невозможными оба дефекта: двойную загрузку и забытое сохранение.
Прежде они предотвращались только дисциплиной — и дважды не предотвратились.

### 2. Правило: сигнал против состояния

* То, что должен увидеть **идущий** turn, — **сигнал**, живёт в процессном реестре
  (`TurnCancellationRegistry`, `ClientRPCService.cancel_all_pending_requests`).
* То, что должно **пережить рестарт**, — **состояние**, живёт в документе сессии
  (`ActiveTurnState.pending_batch`).

Сигнал в состоянии не работает: состояние копируется на запрос. Состояние в реестре не
работает: реестр умирает с процессом. Раньше это было двумя случайными решениями — теперь
правило.

### 3. Долгий turn — последовательность транзакций

Turn не оборачивается в транзакцию. Его возобновляемые данные лежат в документе сессии, а
координация с внешними событиями идёт сигналами. `pending_batch` — образец: остаток батча
переживает круговой обмен с клиентом, потому что записан в состояние.

### 4. Атомарная запись и ревизия

* Запись через временный файл + `os.replace` — закрывает окно порчи документа.
* Поле ревизии и compare-and-set при записи: блокировка защищает внутри процесса, ревизия
  нужна там, где копия живёт через `await` (фоновое исполнение), и обязательна для нескольких
  воркеров.

### 5. Кеширование

Кеш wire-объектов (`CachedSessionStorage`) **не является** механизмом разделения состояния и не
должен им становиться:

* после фазы D порт строит новый агрегат на каждую загрузку — общего состояния кеш не даёт;
* кеш **маскирует забытые сохранения**: P2-42 внутри процесса выглядел бы работающим и терял
  данные только при рестарте;
* выигрыш ничтожен (1.8/4.2 мс).

Если кеш понадобится, его место — **внутри порта, по ревизии, с выдачей снимков**, а не
разделяемых мутабельных объектов.

## Как это ложится на многопользовательский хостинг

Копия на запрос + CAS + атомарная запись = **воркеры без состояния**, сессии на общем
хранилище. Identity map «навсегда» потребовала бы привязки сессии к воркеру.

Принимаемая оговорка: процессные реестры сигналов работают, пока turn исполняется в том
процессе, куда пришёл сигнал. Сегодня это верно. При нескольких воркерах понадобится
маршрутизация по сессии либо перенос сигналов в общую инфраструктуру — решать тогда, отдельным
ADR.

## Отклонённые варианты

**Вернуть кеш в боевой путь** (восстановить решение roadmap 2.1). Отклонено: не даёт общего
состояния после фазы D, маскирует забытые сохранения, выигрыш ничтожен. Проблемы, ради которых
кеш вводился («session not found» после рестарта, OOM от прогрева всех сессий), решаются самим
«читать с диска по id» — что и происходит.

**Единственный экземпляр сессии на процесс (identity map навсегда).** Отклонено: требует
блокировок на весь жизненный цикл, привязки сессии к воркеру при хостинге и превращает
отсутствие записи в невидимый дефект.

**Оставить как есть.** Отклонено: комбинация «копии без CAS, без блокировок, без атомарной
записи» уже дала два дефекта, найденных только разбором живых логов.

## Порядок работ

| Шаг | Объём | Когда |
|---|---|---|
| Атомарная запись | малый | ✅ сделано 2026-07-30 |
| `repository.transaction()` и перевод оставшихся транзакций фазы D на неё | средний | ⏳ область введена, первый потребитель — config-транзакция (2026-07-30) |
| Ревизия + compare-and-set | средний | перед хостингом |
| Разделить горячее состояние и холодный лог (`history`/`events_history` → один источник, статусы — проекция) | крупный | после фазы D; закрывает «честный реплей» P2-42 |

Последний шаг — самый ценный для хостинга: сейчас каждая транзакция перезаписывает 751 КБ, чтобы
изменить один статус. И он же самый инвазивный, поэтому не смешивается с миграцией.

## Ход реализации

**`repository.transaction()` (2026-07-30).** Область: одна загрузка, блокировка на сессию,
запись при успешном выходе, отсутствие записи при исключении. Отдаёт `None`, если сессии нет —
вызывающий возвращает свою ошибку, записи не происходит. Вложенных транзакций нет: повторный
вход по той же сессии внутри области — взаимная блокировка, и это заявлено в docstring.

Первый потребитель — config-транзакция (`session_set_config_option`). Явный `save_session` из
неё убран: забыть запись больше нельзя, а на отказе она не случится.

**Следствие, которое пришлось принять осознанно.** Валидация параметров вынесена **до**
транзакции: иначе отклонённый запрос закрывал бы область коммитом, а запись штампует
`updated_at` — вышла бы ложная «последняя активность» и перезапись всего документа (751 КБ) на
отказ. Наблюдаемое следствие: для несуществующей сессии с неверным параметром клиент получает
`-32602` вместо `-32001`. Порядок закреплён тестом, как и то, что отказ не меняет `updated_at`.

Общий вывод для остальных транзакций: **валидация до области, мутации внутри**. Область не
предусматривает отмены без исключения — намеренно: «забыть abort» было бы той же ошибкой
класса, что «забыть save».

**Атомарная запись: дефект в первой версии.** Имя временного файла было уникально по процессу,
поэтому два одновременных сохранения одной сессии делили один tmp — второй `os.replace` падал с
ENOENT. Поймано полным прогоном тестов (в изоляции проходило), исправлено уникальным именем на
запись. Урок в пользу инварианта: пока запись не атомарна и не сериализована, конкурентные
писатели по одной сессии — реальность, а не гипотеза.

## Что осталось за рамками этого решения

**Две точки входа разошлись.** Кеш недостижим не сам по себе: недостижим `server/cli.py::main`,
который его создаёт (единственный console script — `codelab.cli:main`, путей к `server.cli` из
кода и конфигов нет). При этом `server/cli.py` несёт 26 флагов против 7 у достижимого
`codelab.cli serve` — `--storage`, LLM-переопределения, таймауты, `--auth-api-key`, `--config`,
`--system-prompt`. Это не мёртвый дубль, а более богатая точка входа без пути к ней; удаление
выбросило бы функциональность. Отдельный пункт — не часть этого ADR.

**Запись roadmap 2.1 требует правки:** она описывает `CachedSessionStorage` как единый LRU-кеш
системы со статусом «выполнено», тогда как в работающем сервере его нет.
