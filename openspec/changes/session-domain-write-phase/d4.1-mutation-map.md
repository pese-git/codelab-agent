# D4.1 — Карта чтений/мутаций `SessionState` по под-стейтам

> Вход в фазу D4 (ADR-006). Threaded-объект рабочей модели — `protocol.state.SessionState`,
> тредится как `PromptContext.session` (`context.py:19`), конструируется в
> `prompt_orchestrator.py:206`. Границы транзакции `load→mutate→save` — в командах
> (`session_prompt.py`, `session_load.py`, `session_cancel.py`, `session_new.py`, `config.py`,
> `permission_response.py`, `background_executor.py`, `core.py`).
>
> Карта построена детерминированно (grep + верификация получателя), только по обращениям
> на объекте `SessionState` в `src/codelab/server` (без тестов). Ложные срабатывания
> (LLM-ответы, доменный `Session`, локальные переменные, docstrings) отсеяны.

## 1. plan (`latest_plan`) — 7 сайтов (4W / 3R) [ИСПРАВЛЕНО 2026-07-24]

> **Поправка:** первоначальная карта ошибочно указывала «0 сайтов» (греп-агент пропустил
> обращения вне `session_mapper.py`). Перепроверка надёжным грепом выявила реальную поверхность.

**Записи (4, все — ACP-форма `{content, priority, status}`):**
- `protocol/handlers/plan_builder.py:183` — `session.latest_plan = [...]` (`update_session_plan`)
- `pipeline/stages/directives.py:118` — `context.session.latest_plan = [...]`
- `pipeline/stages/agent_loop/loop.py:452` — `session.latest_plan = list(validated_plan)`
- `pipeline/stages/agent_loop/tool_processor.py:837` — `session.latest_plan = list(plan_entries)`

**Чтения (3):**
- `protocol/handlers/replay_manager.py:325,333` — `replay_latest_plan` (**на `session/load`** — отдельный
  запрос, `domain_session` scaffold там НЕ строится)
- `protocol/handlers/plan_builder.py:195` — `len(session.latest_plan)` (лог)

> **Следствие для b1:** все записи — в protocol-pipeline (флипаемы сейчас). Единственное

## 9. active_turn — 72R/31W, высшая связность (МИГРИРУЕТСЯ ПОСЛЕДНИМ)

`active_turn` (67R/27W) + `pending_prompt_response` (5R/4W). Мутаторы по «весу» жизненного цикла:

1. **`turn_lifecycle_manager.py`** — центр: `create`/`finalize`/`clear`, `set_phase` (:127),

   `permission_request_id`/`permission_tool_call_id`.

4. **`session.py:59-73`** — отмена: `cancel_requested`, `phase="cancelled"`, обнуление.

7. **`permission_manager.py` / `tool_processor.py:336-337` / `prompt/permission_response.py`** —

> **Находки-риски:**

>   → на b4 ввести типизированный `TurnPhase` в доменном `TurnState` VO.
> - `pending_client_request` — под-поле `active_turn`; тип `PendingClientRequestState`.
> - `active_turn` пересекает transport-границу через `pending_prompt_response` (pause/resume).

## Рекомендованный порядок стадий (по возрастанию связности)

Уточняет план design.md (b1→b5) фактическими данными (после поправки счёта plan):

1. **b1 `plan`** — 4W/3R, все записи в protocol-pipeline (флипаемы сейчас); чтение — cross-request
   replay на `session/load`. Флип записей на `domain_session.plan` + dual-carry в `session.latest_plan`.
   Самый изолированный из флипаемых **сейчас**.
2. **b1′ `multi_agent`** — вакуумно (0 рантайм-сайтов). Флипать нечего; зафиксировать долг
   `active_strategy` ↔ `config_values["_active_strategy"]` и мёртвые `task_result`/`sliced_summary`.
3. **`terminals`** — изолировано, но в слое `tools` (`terminal_alias_registry`), где executor получает
   `SessionState`. Флип на `SessionRuntime` VO требует `ToolContext` → **отложено до D3**, не в D4-b.
4. **b3 `tool_calls`** — 2 дублирующих мутатора; решить развилку полей `ToolCallState`.
5. **b4 `history`** — 3 мутатора (`.append`), чтение через порт.
6. **b5 `permissions`** — 6 мутаторов, средняя связность.
7. **b6 `runtime` (events/client-RPC)** — в `SessionRuntime` VO.
8. **b7 `config` (`cwd`/`config_values`/`runtime_capabilities`/`mcp_servers`)** — широкое чтение
   (много `getattr` из agent-слоя), но мало записей; попутно P2-32 (D5.1).
9. **b8 `active_turn`** — **последним** (turn lifecycle, pause/resume, permission, client-RPC,
   transport-граница). Ввести `TurnState` VO с типизированным `TurnPhase` (устранить
   `waiting_permission`/`awaiting_permission` рассинхрон).

Каждая стадия — за golden-wire (D0.1) + round-trip (D0.2) + `make check`.

## Сквозные находки (долги/риски)

1. **Рассинхрон фаз turn:** `"waiting_permission"` (directives) vs `"awaiting_permission"`
   (tool_processor) — строковые литералы без enum. Устранить типизированным `TurnPhase`.
2. **Дублирование tool_call-мутатора:** `tool_call_handler.py` и `prompt/tool_calls.py` — идентичны.
3. **Дублирование стратегии:** `SessionState.active_strategy` ↔ `config_values["_active_strategy"]`.
4. **Duck-typing из agent-слоя:** `getattr(session, "cwd"/"config_values", ...)` в `gatherer.py`,
   `child_session.py`, `dispatcher.py` — при флипе на `domain.Session` учесть эти нестрогие чтения.
5. **Мёртвые поля:** `task_result`, `sliced_summary` (0 сайтов); проверить `session_metrics`,
   `correlation_id` (0 рантайм-сайтов — заполняются ли при сериализации?).
6. **Оценки объёма в design.md устарели** (plan «1», tool_calls «3», active_turn «7») — реальная
   поверхность больше: active_turn 72R/31W, config-чтения ~73.
7. **Два пути исполнения turn'а — resume-путь доминирует** (live-smoke b1, 2026-07-24): помимо основного
   prompt-пути (`prompt_orchestrator.handle_prompt`, где строится `domain_session`), есть
   permission-resume путь `core → background_executor.execute_pending_tool → llm_loop.execute_pending_tool
   → AgentLoop.resume_after_permission`. В реальной сессии он дал **58 из 122** tool-исполнений
   (`background_executor` грузит сессию из storage и `domain_session` НЕ строит). Следствие: под-стейты,
   пишущиеся на resume-пути (`history`, `tool_calls`), для флипа требуют проброса `domain_session` в
   `background_executor`/resume — больше, чем на основном пути. Для `plan` неважно (план на resume не
   пишется; b1-fallback `domain_session=None` → legacy-запись, корректно).
