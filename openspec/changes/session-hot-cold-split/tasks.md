# Расщепление горячего и холодного — Задачи

Каждый шаг: разведка → правка → тесты → `make check` + `lint-imports` → **живой прогон `--stdio`
через Zed** → разбор `~/.codelab/logs/*` → замер → коммит. Шаг не считается закрытым без живого
прогона: за прошлую сессию три вывода были опровергнуты именно измерением.

## Шаг A: горячее уезжает с носителя

> Независим от B. Закрывает остаток P2-58 и остаток P2-32. `schema_version` 8→9.

### A.1 Реестр терминалов → процессный реестр

- [ ] A.1.1 Разведка: все читатели/писатели `SessionRuntime.terminals`, `terminal_counter`,

      `mapping/session_mapper.py`, `protocol/handlers/session.py:262-286`,
      `agent/context/gatherer.py:523-555`). Зафиксировать, кто из них переживает рестарт по смыслу
- [ ] A.1.2 Решение по носителю: процессный реестр рядом с `TurnCancellationRegistry` (правило
      ADR-007 «сигнал против состояния»), ключ — `session_id` + alias. Записать решение в ADR-007
- [ ] A.1.3 Перенести реестр; alias'ы больше не попадают в `SessionDocument`
- [ ] A.1.4 Удалить `terminals_owner`, `PROCESS_TOKEN`, `_drop_terminals_from_previous_process` и
      событие `terminals_dropped_from_previous_process` — после переноса это мёртвый код
- [ ] A.1.5 Ветка «неизвестный терминал» в `TerminalExecutor._resolve_terminal` **остаётся**: она
      корректна и после расщепления (модель может позвать alias из истории), но перестаёт быть
      штатным путём. Проверить, что она даёт `warning`, а не `error`
- [ ] A.1.6 Тесты: alias не персистится; после рестарта реестр пуст без чистки; счётчик терминалов
      не воскресает. Гейт персистентности — **только** `JsonFileStorage`

### A.2 Ссылки на эфемерные ресурсы — проекция при сборке payload'а

- [ ] A.2.1 Разведка: где история попадает в payload модели (`HistoryBuilder`), какие ссылки на

- [ ] A.2.3 Гейт детерминизма: проекция байт-идентична при неизменном состоянии (prompt cache)

### A.3 `runtime_capabilities` принадлежат подключению

## Шаг B1: конверт вместо копии

> Малый, измеренный, без протокольной поверхности. −18.6% документа.

- [ ] B1.1 Подтвердить инвариант на коде, а не только на файле: `content` = конверт над
      `result_content` либо пусто. Источник обоих — `extracted_content.content_items`
      (`tool_processor.py:1100`, `_build_notification_content`). Разобрать, зачем fallback на
      `result.output` даёт расхождение
- [ ] B1.2 Свести к одному полю в `domain/tool_call.py::ToolResult`; конверт накладывает
      `ToolCallMapper` на границе wire. Правило проекта: дубли сводить **переносом**, не удалением
- [ ] B1.3 Отдельно решить судьбу `status=failed`, где `content` пуст, а текст ошибки только в
      `result_content` — после сведения текст ошибки обязан доходить до клиента
- [ ] B1.4 Тесты: round-trip не теряет контент; `failed` несёт текст ошибки; golden-тест wire
- [ ] B1.5 Миграция: старые документы с двумя полями читаются
- [ ] B1.6 Живой прогон + замер: доля `tool_calls` в документе падает с 46% до ≈28%

## Шаг B2: журнал как единственный источник статусов

> Крупный и инвазивный. Не смешивается с миграцией формата — своя `schema_version`.

- [ ] B2.1 Разведка: полон ли `events_history` для восстановления статусов. Измерено:
      53 `tool_call` + 65 `tool_call_update`, все 53 id совпадают с `tool_calls`. Проверить, что
      каждый терминальный статус имеет событие (и наоборот) — на живом файле
- [ ] B2.2 Решение: журнал доменных событий (не ACP-нотификаций) как единственный источник; ACP —
      проекция. Иначе журнал завязан на wire-формат, что противоречит ADR-003/006
- [ ] B2.3 `tool_calls` — проекция журнала: статусы и контент не хранятся отдельно
- [ ] B2.4 Матрица переходов статусов остаётся владельцем правил (урок P2-55: нотификация
      строилась независимо от исхода перехода)
- [ ] B2.5 Тесты: проекция воспроизводит наблюдавшиеся сценарии, включая отмену посреди turn'а и
      ответ клиента на `fs/read_text_file`
- [ ] B2.6 Живой прогон: сверка «`events_history` ↔ статусы `tool_calls`» перестаёт быть
      осмысленной, потому что второго источника нет. Ноль `tool_call_status_transition_rejected`

## Шаг B3: `history` и `events_history` — проекции журнала

- [ ] B3.1 Разведка выводимости. Измерено: `history` = 54 tool + 20 assistant + 3 user;
      сумма `tool_calls` по assistant-записям = 55 при 54 записях role=tool — сойтись обязано,
      расхождение разобрать. `events_history` = 129 событий при 77 записях истории: ни одна
      коллекция не надмножество другой, поэтому журнал должен покрыть **обе**
- [ ] B3.2 Побочно: у assistant-записей истории есть `tool_call_id`, всегда бессмысленный, и
      `content` пуст при заполненном `text` — разобрать перед тем, как воспроизводить в проекции
- [ ] B3.3 LLM-проекция строит **модели**, не `dict` (урок P1-45: союз `HistoryMessage | dict`
      сломал сравнение по префиксу и детерминированно дублировал хвост)
- [ ] B3.4 Golden-тест: LLM-payload байт-идентичен до/после на записанной сессии — иначе рушится
      prompt cache
- [ ] B3.5 Живой прогон + замер: документ ≈675 КБ → ≈180 КБ на сопоставимом прогоне
