# Мультимодальный результат инструмента — Задачи

**Работа разбита на два такта решениями 2026-08-05.** Такт 1 — путь перестаёт терять информацию о
нетекстовом блоке, модель узнаёт о его существовании текстовым описанием. Такт 2 — блок доходит
**данными**; он привязан к двум предпосылкам и здесь только размечен.

Каждый шаг: правка → тесты → `make check` + `lint-imports` → живой прогон `--stdio` через Zed →
разбор `~/.codelab/logs/*` → коммит.

---

## Принятые решения (до кода)

**Р1. Механика для OpenAI-семьи — вариант А: текстовый плейсхолдер в `role: tool`.**
`role: tool` в этой семье обязан быть текстовым по контракту API. Отвергнут вариант Б (плейсхолдер
плюс следующее `role: user` с изображением): он создаёт в истории сообщение, которого в диалоге не
было, — это третий источник правды о содержимом истории, против принципа ADR-007 «история есть
неизменяемый журнал произошедшего», и он же ломает либо реплей (пользователь видит то, чего не
отправлял), либо детерминизм payload'а (сообщение генерируется на лету).

**Р2. Данные изображений в документе сессии — после шага C расщепления (ADR-007), ссылкой, а не
порогом.** Счёт, на котором принято: прогон 2026-08-05 дал документ 362 КБ при ревизии 297; base64
раздувает бинарь примерно на треть, поэтому скриншот на 1 МБ становится ~1.37 МБ в документе, а
пока запись не гранулярна — умножается на число ревизий (≈340 МБ записи за одно изображение).
Порог с плейсхолдером выше него отвергнут как тихий обрыв данных. «Ссылка вместо данных» выбрана,
но **после** шага C: иначе вводим блоб-хранилище и продолжаем перезаписывать документ целиком, то
есть платим за абстракцию, не получив выигрыша.

**Р3. Определение возможностей по модели — предпосылка такта 2.** `litellm`-провайдер объявляет
`supports_vision=True`/`supports_audio=True` **пачкой, не по модели** (`litellm_provider.py:92-99`),
а живая модель — `litellm/openai/MiniMax-M3`. Пока это так, деградация по `supports_vision` не
срабатывает и данные ушли бы в модель, которая их не ждёт.

**Контекст, в котором решения приняты:** живой путь — OpenAI-совместимая семья через litellm;
Anthropic-адаптер у владельца не работает вовсе; MCP-серверов не настроено ни одного (`is_mcp=False`
на каждом вызове живого прогона), то есть замеренный пробел реален в коде, но на живом пути
сегодня недостижим. Приоритет такта 1 — не срочность, а снятие тихой потери данных.

# Такт 1: путь перестаёт терять информацию о блоке

> Инвариант такта: **ни одного нового байта base64 на диске.** Нетекстовые блоки превращаются в
> текстовое описание до записи в историю, поэтому доменный сейм, `HistoryBuilder` и
> `tool_calls[*].content` не меняются.

## Шаг 0: зафиксировать текущее поведение гейтами (до любых правок)

- [x] 0.1 Golden-тест LLM-payload для текстового результата: канон `LLMMessage` и Anthropic-форма,
      `tests/server/agent/test_tool_result_payload_golden.py`. Главный страж prompt cache

      **Гейт вскрыл второй латентный дефект Anthropic-ветки, помимо известного.** Anthropic
      Messages API допускает у сообщения только роли `user` и `assistant`, а `tool_result`-блоки
      кладутся в сообщение с ролью `user`. Наш адаптер копирует роль канона (`anthropic.py:207`),
      поэтому для tool-ответа отдал бы `role: "tool"` — **недопустимую роль**. То есть Anthropic с
      инструментами сегодня не работал бы вовсе. Дефект латентный: живой путь владельца —
      OpenAI-совместимая семья через litellm. Форма закреплена **как есть**, вместе с дефектом,
      чтобы правка была видимой и намеренной
- [x] 0.2 Тест текущей потери: `tests/server/mcp/test_image_result_is_lost.py`. Инструмент,
      вернувший только изображение, даёт `output == ""`, `result.content is None`, а base64
      сохраняется лишь в `raw_output`. Смешанный результат оставляет текст и теряет изображение без
      плейсхолдера. Опорная точка на текстовый результат — чтобы такт 1 его не задел
- [x] 0.3 Замер цены изображения в документе (вход в решение Р2):

      | Что | Бинарь | В документе | Записи за 297 ревизий |
      |---|---|---|---|
      | иконка 64×64 | 4 КБ | 5 КБ | 1.6 МБ |
      | скриншот окна 1280×800 | 900 КБ | 1.2 МБ | **348 МБ** |
      | скриншот Retina 2560×1600 | 3 МБ | 4 МБ | **1.19 ГБ** |

      Base64 даёт ×4/3, число ревизий взято по живому прогону 2026-08-05. Подтверждает Р2: без
      гранулярной записи (шаг C) один скриншот стоит сотни мегабайт записи, и история — журнал
      неизменяемый, то есть «подчистить потом» не вариант

## Шаг 1: рендер блоков в текст получает вызывающего

- [ ] 1.1 Перенести `ContentFormatter._merge_content_items` (`text`/`diff`/`image`/`audio`/
      `embedded` → текст) на путь, питающий `add_tool_result`. Это **перенос, а не удаление**:
      сегодня это единственное место на сервере, которое умеет описать нетекстовый блок словами
- [ ] 1.2 `_add_tool_result_to_history` получает `extracted_content.content_items` и использует
      рендер, когда среди блоков есть нетекстовые. Чисто текстовый результат идёт прежним путём —
      строка не переупаковывается
- [ ] 1.3 Гейт 0.1 обязан остаться зелёным: для текстового результата payload байт-идентичен
- [ ] 1.4 Гейт: рендер нетекстового блока в текст имеет **ровно одну** реализацию на сервере
