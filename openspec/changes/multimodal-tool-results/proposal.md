# Proposal: результат инструмента доходит до модели мультимодально

Найдено при разборе побочной находки шага B1 расщепления (ADR-007): `ContentFormatter` в turn-пути
вычисляет сообщение для LLM и выбрасывает его. Разведка показала, что это не мёртвый код, а
**наполовину подключённый путь**, и за ним стоит функциональный пробел.

## Why

### Пробел, подтверждённый по коду

Нетекстовый результат инструмента не доходит **ни до модели, ни до клиента**. Цепочка из пяти
звеньев, каждое проверено:

1. **MCP-адаптер** (`mcp/tool_adapter.py:241-254`) конвертирует MCP content в ACP-блоки, включая
   `image` с base64 (`mcp/content_mapper.py:81`), затем зовёт `extract_text_from_acp_content`,
   который **молча отбрасывает всё, кроме `type == "text"`** — без плейсхолдера. Блоки уезжают
   только в `raw_output`; `result.content` не задаётся.
2. **Turn-путь** (`_add_tool_result_to_history`) принимает `output: str | None` и `error` — строки.
3. **Доменный сейм** `Session.add_tool_result(tool_call_id, content: str)` — текстовый по подписи,
   зовёт `MessageContent.from_text`.
4. **`HistoryBuilder._convert_history_entry`**: для `role == "tool"` делает `content=str(...)` и
   **не вызывает** `_convert_content_blocks` — мультимодальная ветка применяется к user/assistant
   и намеренно исключена для tool.
5. **Anthropic-адаптер** (`llm/providers/anthropic.py:228-236`) в tool-ветке кладёт `msg.content`
   в `tool_result.content` **как есть**, без `_convert_content_parts_to_anthropic` — единственная
   ветка адаптера, которая не умеет `list[ContentPart]`.

**Наблюдаемое следствие.** MCP-инструмент, вернувший только изображение, даёт `output == ""` →
в историю уходит `"Success"`. Модели сообщается «Success», и о существовании изображения она не
узнаёт никак. Клиент тоже видит лишь текстовый fallback (`ToolResultMapper.to_acp_content` без
`result.content`), а base64 при этом **персистится в документе сессии** внутри `raw_output` — без
читателей и без ограничения размера.

### Половина инфраструктуры уже есть, и не с той стороны, где ожидалось

* `LLMMessage.content` объявлен `str | list[ContentPart]` — канон мультимодальность **уже** допускает.
* `ContentPart` умеет `make_text`/`make_image`/`make_audio`.
* `content_parts_to_openai(parts, supports_vision=..., supports_audio=...)` уже делает graceful
  degradation по возможностям модели (работа по `shared/prompt_capabilities.py`).
* Доменный `MessageContent` — упорядоченные `blocks` с `from_acp_blocks`, то есть **канонический
  носитель мультимодального содержимого в домене уже выбран** и используется для user-сообщений.

Разрыв не в инфраструктуре, а в трёх средних звеньях, которые форсируют текст, и в одном адаптере,
который сломается, если ему дать список.

### Формы сообщений у провайдеров различаются — и различие принципиально

Провайдеров девять, семей форм две:

| Семья | Кто | `role: tool` |
|---|---|---|
| OpenAI-совместимая | `openai`, `openai_compatible`, `openrouter`, `lmstudio`, `ollama`, `litellm`, `zen`, `go` | `{"role": "tool", "tool_call_id", "content"}` — совпадает с внутренним каноном |
| Anthropic | `anthropic` | `{"role": "user", "content": [{"type": "tool_result", "tool_use_id", ...}]}` |

Различие не косметическое: оно определяет, **куда допустимо положить изображение**. Anthropic
принимает блоки контента внутри `tool_result` — там мультимодальный результат выражается напрямую.
В OpenAI-совместимых API `role: tool` держится текстовым, и изображение туда положить нельзя.

Отсюда: «результат доходит мультимодально» нельзя реализовать одной формой для всех — точка
приложения решения не `HistoryBuilder`, а адаптеры провайдеров.

## What Changes

**Работа разбита на два такта решениями 2026-08-05** (Р1 — вариант А для OpenAI-семьи, Р2 — данные
в документе только после шага C ADR-007, Р3 — возможности по модели как предпосылка). Полный список
решений с ценой и отвергнутыми вариантами — в `tasks.md`.

### Такт 1 — путь перестаёт терять информацию о блоке

Инвариант: **ни одного нового байта base64 на диске.** Нетекстовые блоки превращаются в текстовое
описание **до** записи в историю, поэтому доменный сейм, `HistoryBuilder` и `tool_calls[*].content`
не меняются вовсе.

1. `ContentFormatter._merge_content_items` (`text`/`diff`/`image`/`audio`/`embedded` → текст)
   **переносится** на путь, питающий `add_tool_result`, и получает вызывающего. Сегодня это
   единственное место на сервере, которое умеет описать нетекстовый блок словами.
2. MCP-адаптер перестаёт молча терять блоки: они описываются тем же рендером и попадают в `output`.
   `result.content` пока **не** заполняется блоками — это положило бы base64 в документ.
3. `_format_for_openai`/`_format_for_anthropic` удаляются как дубль: канон производит
   `HistoryBuilder`, отклонения от канона живут каждое в своём адаптере провайдера.
4. Закрывается латентный дефект Anthropic-ветки (`msg.content` уходит в `tool_result.content` без
   конвертации `ContentPart`) — дёшево и снимает ловушку такта 2.

### Такт 2 — блок доходит данными (размечен, не начат)

Открывается после **двух** предпосылок: возможности определяются по модели (Р3) и сделан шаг C
расщепления с механизмом «ссылка вместо данных» (Р2). Тогда доменный сейм расширяется до
`str | Sequence[Any]` (идиом `add_user_message`, носитель `MessageContent.blocks`, нового
представления не вводить), `HistoryBuilder` применяет к роли `tool` тот же `_convert_content_blocks`,
Anthropic кладёт блоки внутрь `tool_result.content`, MCP заполняет `result.content`.

## Риски и гейты

* **Детерминизм prompt-payload.** Текстовый результат — подавляющее большинство вызовов; для него
  payload обязан остаться байт-идентичным, иначе рушится prompt cache. Гейт — golden-тест на
  текстовом результате до/после.
* **Конфликт с ADR-007 разрешён решением Р2, а не оговоркой.** Изображения в истории — это base64
  в документе, то есть рост того объёма, который расщепление сокращает; пока запись не гранулярна,
  блоб умножается на число ревизий (прогон 2026-08-05: документ 362 КБ при ревизии 297 → скриншот
  на 1 МБ обошёлся бы ≈340 МБ записи). Поэтому данные переехали в такт 2, за шаг C, а такт 1 несёт
  инвариант «ноль новых base64».
* **OpenAI-совместимые API отвергают нетекстовый `role: tool`.** В такте 1 это и не может
  случиться: до истории доходит текст. Гейт остаётся на такт 2.
* **Возможности объявлены пачкой, а не по модели.** `litellm_provider.py:92-99` заявляет
  `supports_vision`/`supports_audio` максимумом при живой модели `litellm/openai/MiniMax-M3`, то
  есть существующая деградация не сработала бы. Это предпосылка Р3 такта 2, не риск такта 1.
* **Anthropic tool-ветка сегодня отдала бы `ContentPart` в API.** Гейт на это ставится до правки —
  как регресс-тест на латентный дефект.
* **Живым прогоном ветка MCP не покрывается.** MCP-серверов не настроено ни одного (`is_mcp=False`
  на каждом вызове прогона 2026-08-05), поэтому подтверждение — тестами, и это говорится прямо, а не
  подменяется «ошибок нет». По той же причине Anthropic-правка проверяется тестом: живой путь
  владельца — OpenAI-совместимая семья через litellm.

## Приёмка такта 1

* MCP-инструмент, вернувший изображение, больше не даёт модели `"Success"`: она узнаёт о
  существовании нетекстового блока текстовым описанием.
* Текстовый результат: payload байт-идентичен прежнему (golden-тест).
* `ContentFormatter` не содержит провайдерных форм; рендер блоков в текст имеет вызывающего и
  существует в единственной реализации.
* Anthropic tool-ветка конвертирует `ContentPart` (латентный дефект закрыт регресс-тестом).
* Документ сессии **не вырос**: ноль новых base64 — инвариант такта.
* `make check` зелёный, `lint-imports` — 4 контракта kept, живой прогон без `error`/`critical`.

## Вне области

* **Шаг B2 расщепления** (журнал как единственный источник статусов) — не смешивается: там
  меняется хранение, здесь — путь содержимого к модели.
* **P1-56** (гейт разрешений у реестра инструментов) — ждёт решения по служебному режиму.
